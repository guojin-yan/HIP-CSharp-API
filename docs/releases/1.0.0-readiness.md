# 1.0.0 readiness matrix / 发布就绪矩阵

This is the active readiness review for 1.0.0. The table records the sealed 3d626dd candidate; later changes are described separately. The [August matrix](1.0.0-readiness-2026-08.md) and its old API counts are historical. Candidate-specific claims require a clean source commit and exact package hashes; they are not inferred from earlier development results.

## Current release scope / 当前发布范围

The release scope is the managed Core with documented native requirements and
exclusions. Confirmed AMD Runtime defects are deferred to upstream rather than
fixed through private patches in this repository. The [upstream issue register](../guides/upstream-runtime-issues.md)
tracks them, including the existing official typed-fill issue and draft PR.
Pending reports are explicitly marked pending; a prepared report is not a filed
Issue. This scope replaces the earlier goal of repairing every AMD native
implementation before releasing the managed package. It does not turn failing
functions into passing tests or approve local Runtime redistribution.

The latest previously packaged managed logic is `3542567`, with Core SHA-256
`97ae6b4113eeb7b46de24ede7641ecdbf858fdf3491298e26bcc52a910daa554`.
Its Windows package matrix passed 23 cases with 1 capability skip, and WSL passed
21 with 2 capability skips, including the additional interop-boundary fixture.
Managed validation passed 241 tests on each host. Later function fixtures add
local resource evidence without changing that package. The table below remains
the **historical 3d626dd candidate** record, not a current-HEAD attestation. A new
package still requires its own clean source/hash binding and package validation.

Outstanding Core release decisions include the documented support scope, any
unqualified host/resource combinations, current exact-package validation and
production publication setup. A newer native version must be tested independently
before an exclusion is removed. No private Runtime rebuild is a Core release gate.

The previously sealed Core comes from `3d626ddf643e1bfef3a358ea3e26c3e5fedcdf38`, with nupkg SHA-256 `0283698aec534b2d8442f3280468d3f65998ad8dca7938e940f54e82844aaae4`. Those bytes remain unchanged. All cloud logs and summaries have been recovered locally; the completed validation no longer requires the cloud instance.

Subsequent interop boundary fixes change Core: managed descriptor consumers reject default/null descriptors, callbacks obey Runtime/stream disposal and capture checks, and graphics queries reject null-success results. The new `HipAdvancedInteropBoundaryTests` cover these failures and external mapping cleanup with native test doubles. `test-local-runtime-package.ps1 -InteropBoundaries` additionally runs real native callbacks and driver diagnostics. These changes require a new exact package and independent Windows/Linux validation; the recorded 3d626dd KFD receipts and 7 reviewed function passes remain attached only to the older package. They do not establish KFD coverage for the changed Core or close external-resource/multi-GPU or redistribution gates.

`HipInteropRollbackTests` additionally reproduce failed submission plus failed native cleanup: a lost last-borrow object could prevent owner cleanup retry, one failure could strand the other borrows, and failed graphics rollback could strand stream ownership. Cleanup now returns all borrows, permits retry through the owner or retained lease without double release, and always returns stream ownership after failed mapping. These are injected-error regressions, not valid external-resource GPU fixtures.

## Meaning of completion / 完成条件

An unavailable native function or an unsupported hardware capability must return an explicit failure or supported capability result; it must never be counted as successful execution. The 1.0.0 package can be constructed while this matrix remains blocked. A stable version number does not clear the full-interface requirement or external prerequisites.

Cloud evidence is kept outside source under `Radeon_Cloud/records/20261115-3d626dd-release-candidate`. The raw recovery archive SHA-256 is `8c66515389bf6b47a7ab0c864a77e4c5d1104def1b7b137d692cff4c174d74bc`. The function ledger binds five raw IPC entries and two managed physical-sharing entries to `eng/interface-coverage/reviewed-function-evidence.json`, including the tested source, Core hash, fixture hash, two Runtime packages, summaries and logs. Recheck the recovered files offline with `python -B eng/interface-coverage/verify-function-evidence.py --workspace <external-workspace>`. Inventory-only checks do not verify execution. These pins do not establish current-HEAD GPU or full negative coverage, or upgrade unrelated interfaces.

POSIX descriptors use signed 32-bit values, including zero. Both tested native runtimes exported descriptor zero successfully but rejected its import with `InvalidValue`; the managed layer now propagates that native error. Positive-descriptor import and shared mapping/lifetime checks passed. Native restrictions are not converted into successful function executions.

The [local native function fixtures](../guides/native-function-validation.md) extend the current exact `3542567` Core's local validation without changing those package bytes or the historical KFD ledger. New Windows/WSL direct-native controls reproduce incorrect width handling in four 16/32-bit two-dimensional memset functions and inconsistent primary-context state/flag behavior in the local 10.1.0 Runtime. These remain release blockers for a claim that every interface works; full results must retain failures and deprecated-context/WSL capability restrictions. The fixture tool commit is distinct from the Core source commit.

Extended native controls also reproduce driver-link bitcode rejection on both hosts, zero texture-linear width on WSL, and successful-but-ineffective Windows batch stream/graph memory writes. Linux batch operations pass; scalar stream writes pass on both hosts. Compiler-registered host kernel/global-symbol fixtures, occupancy queries, library/driver texture descriptors, graph parameter updates, capture extension and batched copies add data and lifecycle assertions, without clearing unrelated resource or publication gates.
