# 0.9.0 Linux release candidate / Linux 发布候选

`JYPPX.ROCm.HIP.CSharp.API` version `0.9.0` and optional Linux Runtime `7.2.1` were published on 2026-08-14. The Core package was then found to carry the unintended `JYPPX.ROCm.HipSharp` assembly identity. NuGet versions are immutable, so `0.9.0` is retained as an incident artifact and must not be replaced in place. Consumers should wait for the `0.9.1` forward fix.

`JYPPX.ROCm.HIP.CSharp.API` `0.9.0` 与可选 Linux Runtime `7.2.1` 已于 2026-08-14 发布。随后确认 Core 包误用了 `JYPPX.ROCm.HipSharp` 程序集 identity。NuGet 版本不可变，因此 `0.9.0` 只作为事故产物保留，不能原位替换；消费者应等待 `0.9.1` forward fix。

This package adopts the `JYPPX.ROCm.HipSharp` namespace, but its assembly identity did not match the intended `JYPPX.ROCm.HIP.CSharp.API` package identity. See the [migration decision](../design/jyppx-rocm-naming-migration.md) and the [forward-fix release note](0.9.1-forward-fix.md).

该包采用 `JYPPX.ROCm.HipSharp` 命名空间，但程序集 identity 未与预期的 `JYPPX.ROCm.HIP.CSharp.API` 包 identity 对齐。参见[迁移决策](../design/jyppx-rocm-naming-migration.md)和 [forward-fix release note](0.9.1-forward-fix.md)。

The committed API snapshot is checked against all 15 target frameworks. The selected managed owners are driven by a 100-entry interop manifest: 91 HIP Runtime and 9 HIPRTC entries. M8.6 adds `hipModuleGetGlobal` for borrowed byte/typed module symbol views after M8.5's six module-kernel entries. The complete low-level model remains 459 HIP Runtime and 18 HIPRTC C ABI declarations from the pinned official headers; 368 Runtime and 9 HIPRTC declarations remain low-level-only. The formal/diagnostic/sample-only/internal classification, ownership and disposal rules, thread-safety limits, error model, and permitted pre-freeze changes are recorded in the [API freeze review](../guides/api-freeze.md).

Local candidate requirements are fail-closed:

- one central version source for Core `0.9.0`, Linux Runtime `7.2.1`, and the disabled Windows Runtime `7.2.0` skeleton;
- deterministic interop generation from the 100-entry owner manifest plus the pinned-header complete model, with identical public API on all TFMs;
- build, unit, quality, package, clean-consumer, documentation, source-provenance, closure, license, SBOM, size, and static Windows gates;
- exact Git commit metadata in both packages, a receipt locked to the M8.7 candidate, and a candidate/final payload-equivalence report;
- `publishable=false` and `releaseAuthorized=false` until the final Core and Runtime package bytes pass a newly Owner-authorized official-host and package-only PRoot GPU gate.

M8.7 validated the exact `4d8edb29daa7a25b50aeaf42938df90320f628fa` candidate on both official-host and Ubuntu Base + PRoot package-only paths. It passed Runtime `91/91`, HIPRTC `9/9`, complete Runtime `458/459` with the single reviewed `hipExternalMemoryGetMappedMipmappedArray` exception, complete HIPRTC `18/18`, schema-7 ABI, all five managed stages with 1,127 CPU/GPU comparisons, the bounded 10-round reliability run, and four fail-closed isolated negatives. P2P was honestly recorded as `skipped(device-count<2)` and no performance claim was made.

M8.8 records that evidence in a deterministic receipt and requires candidate/final payload equivalence. Exact final Git and package identities are generated after the clean promotion commit and are kept in the external release envelope to avoid a self-referential commit/package hash. Until those final bytes pass a newly authorized final-mode gate, the stage is blocked rather than release-ready. Windows remains disabled, inventory-empty, static-audit-only, and GPU-unvalidated.
