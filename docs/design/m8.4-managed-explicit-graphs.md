# M8.4 managed explicit graph design

This feature adds an explicit HIP graph builder without exposing native graph-node handles,
parameter structures, or unmanaged dependency arrays.

## Graph modes and identity

- `HipGraph` has either captured or explicit mode. A captured graph keeps the existing
  capture/instantiate/launch behavior, but rejects builder and managed-topology APIs because its
  nodes were not created by this wrapper. An explicit graph is created by `HipRuntime.CreateGraph`.
- `HipGraphNode` is a graph-owned borrowed identity, not a `SafeHandle`. Its native handle is never
  public. It is valid until its graph is successfully destroyed. Failed node creation never creates
  a public node. High-level node removal is deliberately absent, so a successful node identity is
  stable for the graph lifetime.
- Explicit graphs become immutable after the first successful instantiation. This makes every
  executable's topology and initial resource snapshot provable. Further node creation, dependency
  mutation, and graph-node parameter mutation are rejected. Executable parameter updates remain
  available independently.

## Dependencies and introspection

Dependencies are directed from prerequisite to dependent. The builder validates null entries,
duplicate dependencies, self edges, cross-graph nodes, disposed graphs, duplicate edges, and cycles
before calling HIP. Native arrays are allocated internally for the duration of a call. Managed
topology changes are committed only after native success, so retry behavior is deterministic.

`Nodes`, `RootNodes`, `Edges`, node `Type`, and node dependencies are read-only snapshots of the
managed explicit DAG. Native two-call topology queries remain low-level: using them as a second
source of truth would allow unmanaged mutation to make the high-level graph inconsistent. Raw
low-level calls and the managed builder must not be mixed for the same graph.

## Typed operation nodes

- Kernel nodes reuse `HipKernel`, `HipKernelArgument`, and the same dimension validation and argument
  marshalling used by direct launches. A persistent parameter snapshot owns scalar storage, the
  parameter-pointer array, a module reference, and device-memory pointer references. Graph-local
  arguments are accepted only for the same graph and never become normal pointer owners.
- Memcpy nodes support safe one-dimensional device-to-device copies between `HipDeviceMemory` and/or
  graph-local memory. Byte counts are nonzero, fit `size_t`, and cannot exceed either operand.
- Memset nodes support one-dimensional byte-pattern fills. Their verified native parameters use
  element size one, height one, pitch zero, and width equal to the checked byte count.
- Pitched 2D/3D copies, arrays, symbols, host pointers, peer pointers, and arbitrary pointers remain
  low-level. They need additional operand and pitch contracts and are not approximated here.

## Graph-local memory

`HipGraphMemory` is a graph-scoped reference returned by `AddMemoryAllocation`. It exposes byte count,
device, and its allocation node, but no native pointer and no `Dispose`. Internally the allocation
node uses pinned allocation properties, no shareable handle, an optional typed device-access list,
and the pointer written by `hipGraphAddMemAllocNode`.

Only later nodes in the same graph may consume the reference. A consumer must transitively depend on
its allocation node. `AddMemoryFree` creates the sole free node; it must transitively depend on every
registered consumer. Consumers cannot be added after the free node, duplicate free is rejected, and
instantiation rejects an allocation without a matching free. Each executable launch therefore
orders allocation, all consumers, and one free. Repeated launches repeat that native DAG; managed
code never independently frees or exports the graph pointer.

## Shared resources and executable lifetime

Captured leases and explicit-node snapshots use one reference-counted `HipGraphResources` store.
The graph owns the initial reference and each executable acquires another. Destroying the source
graph first therefore leaves modules, pointer owners, scalar storage, and graph allocation metadata
alive for executable launches. The last graph/executable owner releases resources in reverse order.

Launch takes a `SafeHandle` reference and transfers it to the stream pending-lease queue. Executable
disposal waits for all pending launches; stream synchronization, successful query, or stream disposal
releases those references. Upload is synchronous submission setup and does not create a pending
lease. Graph and executable operations serialize their managed state with private locks; callers must
still coordinate unrelated low-level native calls.

## Updates and failures

The high-level update contract uses `hipGraphExecKernelNodeSetParams`,
`hipGraphExecMemcpyNodeSetParams1D`, and `hipGraphExecMemsetNodeSetParams`. An executable accepts only a
node from the explicit graph that instantiated it, with the matching node type. Updates are rejected
while a launch is pending. New snapshots are validated and acquired before the native call; native
failure disposes the candidate and preserves the old executable and resources. Success atomically
replaces the managed update snapshot.

`hipGraphExecUpdate` remains low-level because whole-graph replacement can change node identity and
resource mapping in ways that cannot be reconstructed from its result enum alone. Graph-node set/get
parameter calls likewise remain low-level because explicit graphs are sealed at instantiation. The
ABI probe still records the update-result enum for future work.

## ABI and errors

Internal sequential structures mirror the pinned HIP 7.2.1 declarations:
`hipKernelNodeParams` is block dimensions, extra pointer, function, grid dimensions, kernel-parameter
pointer, and shared-memory bytes; `hipMemsetParams` is destination, element size, height, pitch,
value, and width; `hipMemAllocNodeParams` embeds `hipMemPoolProps`, access descriptors/count, byte
count, and returned device pointer. Pointer-width sizes and every field offset are gated by managed
tests and added to the native ABI probe for later official-header execution.

All graph exports in this family are optional. Missing exports produce the existing stable
`HipException`/`HipError.NotSupported` behavior and never fall back to stream capture. Partial graph
and executable handles are destroyed when possible. Explicit destroy failures retain ownership for
retry; `SafeHandle` final release never throws.

## Deliberately low-level capabilities

Host/callback nodes, child graphs, event nodes, external semaphores, batch memory operations,
conditional graphs, symbol/array copies, raw parameter injection, arbitrary pointers, native
introspection, node destruction, graph cloning, and whole-graph executable update remain low-level.
