# M8.5 managed kernel capability, occupancy, and cooperative launch

## Scope

M8.5 extends the module-owned `HipKernel` path. It does not reinterpret compiler function
addresses as module handles and does not create a second kernel owner. The high-level path uses
only APIs whose function argument is `hipFunction_t`:

- `hipFuncGetAttribute`
- the four `hipModuleOccupancy*` variants
- `hipModuleLaunchCooperativeKernel`

Runtime occupancy and `hipFuncGetAttributes`/`hipFuncSet*` variants accept `const void*` compiler
function addresses and remain low-level. Multi-device cooperative launch also remains low-level
because it needs a cross-device launch-list owner and partial-failure contract.

## Public model

`HipKernelAttributes` is an immutable aggregate. `HipKernel.GetAttributes()` queries the selected
portable resource fields one at a time while the module handle is retained: maximum threads per
block, static shared bytes, constant bytes, local bytes per thread, registers per thread, binary
version, and maximum dynamic shared bytes. Negative native results fail closed. PTX version,
cache mode, and preferred shared-memory carveout are deliberately excluded because their meaning
is backend-specific or policy-oriented rather than a portable resource fact.

`HipOccupancyInfo` describes a caller-selected block size: active blocks per multiprocessor,
multiprocessor count, and their checked product. `HipOccupancyPlan` adds the native minimum grid
size and suggested block size, then queries `HipOccupancyInfo` for that block. Sizes are explicit:
block size is threads, grid size is blocks, and dynamic shared memory is bytes. Occupancy is a
resource-residency estimate, not a performance claim.

`HipOccupancyFlags.Default` calls the non-flags native entry point. The only nonzero public flag,
`DisableCachingOverride`, is the pinned header value `0x01` and calls the corresponding WithFlags
entry point. Unknown bits are rejected before native code. A block-size limit of zero preserves
the native "kernel maximum" meaning; negative limits are rejected.

## Device capability

The pinned ROCm 7.2.1 header assigns `CooperativeLaunch=11`, `MultiprocessorCount=64`, and
`WarpSize=89`. These values are added to the existing typed device-attribute allowlist without
changing previously frozen enum values. `HipDevice` exposes typed convenience properties for
these three facts and validates boolean/positive native results.

Kernel attribute and occupancy calls require the current device to equal the device on which the
module was loaded. Cooperative launch additionally requires an explicit stream, when supplied,
to belong to that same runtime and device. The library never changes the caller's current device.

## Cooperative launch

`HipKernel.LaunchCooperative` has default-stream and explicit-stream overloads. Both reuse the
ordinary launch dimension validator and one internal argument marshaller. Graph-local pointers
remain graph-only; stream-ordered pointers must use their required stream; cross-runtime,
cross-device, disposed, null, and overflow inputs fail before the launch call.

Before submission the method:

1. verifies the module device is current;
2. verifies the device reports cooperative-launch support;
3. queries active blocks for the requested block size and dynamic shared memory;
4. computes `active blocks * multiprocessor count` with checked arithmetic; and
5. rejects a grid whose block product exceeds that resident capacity.

HIP remains the final legality authority. The managed limit prevents a known invalid submission
but does not promise that a launch is fast or that every later runtime constraint is predictable.
Missing cooperative or occupancy exports return the established `HipError.NotSupported` path;
there is no fallback to ordinary launch because that would remove grid-wide synchronization.

For an explicit stream, the module and every pointer owner are retained until query,
synchronization, or stream disposal drains the pending lease. Parameter storage is released after
the native submission returns, matching the existing module-launch contract. Default-stream
launch retains no asynchronous lease; as with the existing default launch, callers must keep
owners alive and synchronize before disposal.

## Failure and concurrency

All query and launch calls execute while `HipModule.Invoke` prevents module disposal. An explicit
stream launch acquires module and pointer references before the native call and transfers them to
the stream only on success. Failure releases every acquired reference and registers no pending
work. Lease cleanup advances only after each release succeeds, preserving retry behavior already
used by the stream resource model.

Module operation/disposal races remain unsupported outside these serialized transitions. No new
SafeHandle is introduced: kernel identity, attributes, occupancy information, flags, and launch
dimensions are borrowed identities or values, not independently releasable native resources.

## Evidence boundary

The ABI probe records the function-attribute enum, occupancy flag, and new device-attribute values,
and statically asserts the six signatures against the pinned header set. Local fake-native tests
prove marshaling, routing, validation, and lifetime only. Real exports, runtime behavior, occupancy
results, and cooperative GPU execution require a separately authorized Radeon Cloud session.
