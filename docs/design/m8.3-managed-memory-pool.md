# M8.3 managed memory pool design

This feature exposes process-local HIP memory pools without exposing native pool handles, raw
attribute integers, or native structures.

## Ownership and identity

- `HipMemoryPool` is the single public pool view. A pool created by `HipRuntime.CreateMemoryPool` is
  owned and destroys its native handle. The default-pool view is Runtime-owned and borrowed. A
  current-pool view is always borrowed but may refer to either the Runtime default or a custom pool;
  it therefore never extends a custom owner's lifetime and never calls `hipMemPoolDestroy`.
  `OwnsHandle` makes the distinction observable, while the native handle remains internal.
- Every pool records its `HipRuntime` client and device ordinal. Every operation validates the same
  native client and device before calling HIP. Two managed views may refer to the same borrowed
  native pool, but neither owns it.
- `HipMemoryPoolOptions` accepts a `HipDevice` from the creating runtime. The custom pool maps to
  pinned HIP 7.2.1 ABI values: pinned allocation type, no shareable handle type, a device
  `hipMemLocation`, and an optional byte maximum (zero selects HIP's system-dependent limit).
  Shareable handle options are deliberately unavailable.

## Current-pool lifetime

`HipMemoryPool.UseAsCurrent` returns `HipMemoryPoolCurrentScope`. Creation reads the previous pool,
sets the selected pool, and holds a current-use reference on an owned pool. Scope disposal restores
the exact previous borrowed handle before releasing that reference. Scopes are device-wide native
state and therefore must be disposed in LIFO order; disposal refuses an out-of-order scope. An owned
pool cannot be destroyed while a scope keeps it current. A restore error is reported and the scope
can be disposed again.

## Allocation and stream ordering

- `HipPooledDeviceMemory` is a distinct owner because it must retain both its allocation stream and
  its source pool until the stream-ordered `hipFreeAsync` completes. Its copy surface follows
  `HipAsyncDeviceMemory`: managed arrays are pinned, the pointer owner is leased, and completion is
  observed through stream `Synchronize`, successful `Query`, or stream disposal.
- `AllocateAsync` registers the allocation as a stream-owned resource before
  `hipMallocFromPoolAsync`. It also registers a child with the pool. Submission failure releases both
  registrations and cleans up any partial pointer with `hipFreeAsync`; there is no fallback to
  `hipMallocAsync`.
- Explicit memory disposal submits `hipFreeAsync` on the allocation stream. The allocation remains a
  pool child and a stream-owned resource until a completion lease runs. Consequently the stream and
  pool cannot be destroyed between free submission and completion. A submission error preserves the
  owner for retry. SafeHandle final release attempts the same native free and never throws.
- Graph capture is not supported for pool allocation or release in this high-level feature. Graph
  allocation/free nodes require a separate ownership design.

## Policy and statistics

The managed property mapping is fixed and strongly typed:

| Managed property | Native attribute | Width | Unit | Access |
| --- | --- | --- | --- | --- |
| `ReleaseThresholdBytes` | `ReleaseThreshold` (4) | 64-bit | bytes | read/write |
| `AllowEventDependencyReuse` | `ReuseFollowEventDependencies` (1) | 32-bit | boolean | read/write |
| `AllowOpportunisticReuse` | `ReuseAllowOpportunistic` (2) | 32-bit | boolean | read/write |
| `AllowInternalDependencyReuse` | `ReuseAllowInternalDependencies` (3) | 32-bit | boolean | read/write |
| `ReservedBytes` | `ReservedMemCurrent` (5) | 64-bit | bytes | read-only |
| `ReservedHighWatermarkBytes` | `ReservedMemHigh` (6) | 64-bit | bytes | read/reset-to-zero |
| `UsedBytes` | `UsedMemCurrent` (7) | 64-bit | bytes | read-only |
| `UsedHighWatermarkBytes` | `UsedMemHigh` (8) | 64-bit | bytes | read/reset-to-zero |

Boolean buffers use the native four-byte `int`; byte quantities use the native eight-byte
`uint64_t`. High-watermark reset has explicit methods so callers cannot write an arbitrary value to
a statistic. `HipMemoryPoolStatistics` is an immutable snapshot.

## Access and trimming

- `HipMemoryPoolAccess` is a closed enum mapping `None` (0) and `ReadWrite` (3).
  `HipMemoryPoolAccessDescriptor` is an immutable device/access pair. `SetAccess` rejects empty
  arrays, invalid flags, another runtime, and a device outside the creating runtime. Native
  descriptors contain only the verified device `hipMemLocation` plus 32-bit access flags.
- `GetAccess` accepts a managed `HipDevice` and returns the typed enum. No host or raw location can be
  injected through the high-level API.
- `TrimTo` passes a byte minimum directly to `hipMemPoolTrimTo`. It does not synchronize streams.
  The caller must first establish stream completion when deterministic reclaim is required; HIP may
  retain live or pending allocations above the requested minimum.

## ABI and error behavior

Internal sequential structs mirror the pinned HIP 7.2.1 header: `HipMemPoolPropertiesNative`
contains allocation type, handle types, device location, and two reserved arrays; the x64 size and
offsets are ABI-gated. `HipMemAccessDescriptorNative` contains the location and 32-bit flags. These
types never enter the public API.

All native failures pass through `HipCall` and retain the exact operation name. The 11 pool exports
are optional; an unavailable export becomes a stable `HipException` with `HipError.NotSupported`.
Pool-specific allocation never silently changes policy by falling back to the default allocator.
Explicit pool destruction and free submission can be retried. SafeHandle final release cannot throw.
Public objects use locks for their own state, but HIP device current-pool state is process-wide;
applications must coordinate changes made outside `HipMemoryPoolCurrentScope`.

## Deliberately low-level capabilities

Shareable pool handle and pointer import/export, IPC and OS-handle ownership, graph allocation/free
nodes, virtual memory, external memory, and raw pool-handle injection remain low-level APIs. They need
separate process, security, platform, and ownership contracts.
